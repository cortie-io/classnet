IP 패킷에 목적지 IP 주소를 적었다고 바로 배달되는 것은 아니에요. 같은 LAN 안에서 실제로 프레임을 전달할 때는 MAC 주소가 필요하기 때문이에요. 이 단원에서는 IP 주소로 MAC 주소를 알아내는 ARP, 문제가 생겼을 때 상황을 알려 주는 ICMP, 멀티캐스트 그룹 가입을 관리하는 IGMP를 배워요. 셋 다 IP 곁에서 일하는 도우미 프로토콜이고, `ping`과 `tracert` 같은 진단 도구의 원리가 여기서 나와요.

> [!GOAL]
> - ARP 요청·응답의 전송 방식과 ARP 캐시의 역할을 설명할 수 있다.
> - 프록시 ARP, Gratuitous ARP, RARP의 차이를 구분할 수 있다.
> - 주요 ICMP 유형 번호의 의미와 ping·traceroute의 동작 원리를 안다.
> - IGMP가 하는 일과 버전별 차이를 말할 수 있다.

## ARP — IP 주소로 MAC 주소 찾기

### 왜 필요할까

강의실에서 "민수"라는 이름은 아는데 얼굴을 모른다면 어떻게 할까요? 모두에게 들리게 "민수 학생, 손 들어 주세요!"라고 외치면 민수만 손을 들고 대답하겠죠. 그다음부터는 얼굴을 기억해 두고 바로 찾아가면 돼요.

ARP(Address Resolution Protocol, 주소 결정 프로토콜)가 바로 이 일을 해요. 이더넷 같은 LAN은 MAC 주소를 보고 프레임을 배달하는데, 응용 프로그램과 IP는 IP 주소만 알고 있어요. 그래서 **IPv4 주소를 MAC 주소로 바꿔 주는** 과정이 필요해요. ARP 메시지는 IP 패킷에 담기지 않고 이더넷 프레임에 바로 실려요(EtherType 0x0806). TCP/IP 모델에서는 인터넷 계층 프로토콜로 분류하지만, OSI 기준으로는 2계층과 3계층을 잇는 프로토콜로 보기도 해요.

### 동작 과정

같은 네트워크에 있는 PC A(192.168.10.11)가 PC B(192.168.10.22)에게 처음으로 패킷을 보내는 상황이에요.

1. A는 먼저 자기 **ARP 캐시**(ARP Cache)에 192.168.10.22의 MAC 주소가 있는지 확인해요. 없어요.
2. A가 **ARP 요청**(ARP Request)을 보내요. 목적지 MAC을 `FF-FF-FF-FF-FF-FF`로 하는 **브로드캐스트**예요. 내용은 "192.168.10.22를 쓰는 분, MAC 주소를 알려 주세요. 저는 192.168.10.11, MAC은 02-00-00-00-00-0A예요."
3. 같은 LAN의 모든 호스트가 이 요청을 받지만, 자기 IP가 아닌 호스트는 무시해요.
4. B가 **ARP 응답**(ARP Reply)을 A에게만 **유니캐스트**로 보내요. "192.168.10.22는 저고, MAC은 02-00-00-00-00-0B예요."
5. A는 받은 정보를 ARP 캐시에 저장하고, 이제 B의 MAC 주소로 프레임을 만들어 보내요.

```text
  [A] ---- ARP 요청 (브로드캐스트) ----> 모든 호스트
           "192.168.10.22의 MAC은?"

  [A] <--- ARP 응답 (유니캐스트) ------- [B]
           "02-00-00-00-00-0B입니다"
```

B도 요청 안에 들어 있던 A의 IP와 MAC을 자기 캐시에 기록해 둬요. 곧 A에게 답장을 보낼 가능성이 높기 때문이에요.

> [!WARNING]
> 목적지가 **다른 네트워크**에 있으면, PC는 목적지 호스트의 MAC이 아니라 **기본 게이트웨이(라우터)의 MAC**을 ARP로 알아내요. ARP 요청은 브로드캐스트라서 라우터를 넘어가지 못하거든요. 패킷을 받은 라우터가 다음 구간에서 다시 ARP를 해서 다음 장비의 MAC을 알아내요.

### ARP 캐시

매번 브로드캐스트를 보내면 네트워크가 시끄러워지니, 알아낸 결과는 ARP 캐시(ARP 테이블)에 잠시 저장해요. 자동으로 배운 **동적(Dynamic)** 항목은 일정 시간이 지나면 지워지고(유지 시간은 운영체제마다 달라요), 관리자가 직접 넣은 **정적(Static)** 항목은 지우기 전까지 남아 있어요.

Windows에서는 다음과 같이 확인하고 관리해요(삭제·추가는 관리자 권한 필요).

```powershell
arp -a                                  # ARP 캐시 보기
arp -d *                                # ARP 캐시 전체 삭제
arp -s 192.168.10.1 02-00-00-00-00-01   # 정적 항목 추가
```

리눅스에서는 `ip` 명령을 쓰는 것이 기본이고, net-tools 패키지가 깔려 있으면 `arp`도 쓸 수 있어요.

```bash
ip neigh show    # ARP(이웃) 캐시 보기
arp -n           # net-tools가 설치된 경우
```

명령어의 자세한 옵션은 [Windows 네트워크 명령어](/textbook/nos-windows-commands)에서 다시 다뤄요.

### 프록시 ARP

프록시 ARP(Proxy ARP)는 라우터가 **다른 네트워크에 있는 호스트 대신** ARP 요청에 응답해 주는 기능이에요. 라우터는 자기 MAC 주소를 알려 주고, 이후 그 주소로 들어온 프레임을 받아서 실제 목적지 쪽으로 전달해요. 서브넷 마스크를 잘못 설정했거나 기본 게이트웨이가 없는 호스트도 다른 네트워크와 통신할 수 있게 되지만, ARP 테이블이 커지고 잘못된 설정을 감추게 되는 단점이 있어요.

### Gratuitous ARP

Gratuitous ARP(GARP, "청하지 않은 ARP")는 호스트가 **자기 자신의 IP 주소**에 대해 보내는 ARP예요. 쓰임새는 두 가지예요.

- **IP 주소 충돌 감지**: 부팅하거나 IP를 새로 받을 때 "이 IP를 쓰는 분 있나요?"라고 물어요. 누군가 응답하면 충돌이에요. 운영체제의 "IP 주소 충돌" 경고가 이런 확인 과정에서 나와요.
- **다른 호스트의 ARP 캐시 갱신**: 네트워크 카드를 바꾸거나, 이중화된 게이트웨이·서버에서 대기 장비가 역할을 넘겨받았을 때 "이 IP의 MAC이 바뀌었어요"라고 미리 알려요.

### RARP와 그 후계자

RARP(Reverse ARP)는 이름 그대로 반대 방향, **MAC 주소로 자기 IP 주소를 알아내는** 프로토콜이에요. 저장 장치가 없어 IP 설정을 저장할 수 없는 디스크 없는 워크스테이션(Diskless Workstation)이 부팅할 때 썼어요.

하지만 RARP는 한계가 뚜렷했어요.

- 2계층 브로드캐스트로 동작하므로 라우터를 넘지 못해, **네트워크마다 RARP 서버**가 있어야 했어요.
- IP 주소 하나만 알려 줄 뿐 서브넷 마스크, 기본 게이트웨이, DNS 서버 같은 정보는 줄 수 없었어요.

그래서 IP·UDP 위에서 동작하는 **BOOTP**로 대체되었고, 지금은 BOOTP를 발전시킨 **DHCP**를 써요([DNS와 DHCP](/textbook/tcpip-dns-dhcp)에서 배워요).

| 프로토콜 | 아는 것 → 알아내는 것 | 메모 |
|---|---|---|
| ARP | IP 주소 → MAC 주소 | 요청 브로드캐스트, 응답 유니캐스트 |
| RARP | MAC 주소 → IP 주소 | BOOTP·DHCP로 대체됨 |
| 프록시 ARP | 다른 네트워크 IP → 라우터가 대신 응답 | 라우터의 MAC을 알려 줌 |
| Gratuitous ARP | 자기 IP → 자기 MAC 알림 | 충돌 감지, 캐시 갱신 |

> [!NOTE]
> 프레임 릴레이 같은 WAN에서는 2계층 주소(DLCI)로 상대의 IP를 알아내는 Inverse ARP(InARP)를 써요. 이름이 비슷한 RARP와 헷갈리지 않도록 "RARP는 내 IP, InARP는 상대 IP"로 구분해요.

### ARP 스푸핑

ARP에는 인증 기능이 없어서, 요청하지 않은 ARP 응답도 받아들여 캐시를 고쳐 버려요. 공격자는 이 점을 노려 "게이트웨이 192.168.10.1의 MAC은 (공격자의 MAC)"이라는 가짜 응답을 계속 보내요. 그러면 피해자의 패킷이 게이트웨이 대신 공격자에게 먼저 가고, 공격자는 내용을 엿보거나 바꾼 뒤 넘겨줄 수 있어요. 이것을 ARP 스푸핑(ARP Spoofing) 또는 ARP 캐시 포이즈닝이라고 해요.

`arp -a` 결과에서 **서로 다른 IP 두 개가 같은 MAC 주소**로 나온다면 의심해 봐야 해요. 막는 방법으로는 게이트웨이를 정적 ARP 항목으로 등록하기, 스위치의 동적 ARP 검사(Dynamic ARP Inspection) 기능 쓰기 등이 있어요. 공격 기법은 [네트워크 보안 기초](/textbook/tcpip-security-protocols)에서 더 다뤄요.

## ICMP — 오류와 진단 메시지

### ICMP의 역할

택배가 배달되지 못하면 "수취인 불명" 쪽지와 함께 돌아오죠. ICMP(Internet Control Message Protocol)는 IP 통신에서 이런 쪽지 역할을 해요. IP는 오류가 나도 스스로 알리지 않기 때문에, 라우터나 목적지 호스트가 ICMP 메시지로 **출발지에 문제를 보고**해요. ICMP는 문제를 알려 줄 뿐 직접 고치지는 않아요.

ICMP 메시지는 IP 패킷 안에 담겨 전달되고, 이때 IP 헤더의 프로토콜 번호는 **1**이에요. ICMP 헤더는 유형(Type) 8비트, 코드(Code) 8비트, 체크섬(Checksum) 16비트로 시작해요. 유형이 큰 분류이고, 코드가 세부 이유예요.

### 꼭 알아야 할 ICMP 유형

ICMP 메시지는 문제를 알리는 **오류 보고 메시지**와, 상태를 묻고 답하는 **질의 메시지**로 나눠요.

| 유형 | 이름 | 분류 | 언제 쓰나 |
|---|---|---|---|
| 0 | Echo Reply | 질의 | ping에 대한 응답 |
| 3 | Destination Unreachable | 오류 보고 | 목적지(네트워크·호스트·포트)에 도달할 수 없음 |
| 4 | Source Quench | 오류 보고 | 송신 속도를 줄이라는 요청. 지금은 쓰지 않도록 폐기됨 |
| 5 | Redirect | 오류 보고 | 같은 네트워크에 더 나은 게이트웨이가 있음(경로 재지정) |
| 8 | Echo Request | 질의 | ping 요청 |
| 11 | Time Exceeded | 오류 보고 | TTL이 0이 됨, 또는 단편 재조립 시간 초과 |
| 12 | Parameter Problem | 오류 보고 | IP 헤더 값이 잘못됨 |
| 13 / 14 | Timestamp Request / Reply | 질의 | 상대 호스트의 시간 확인 |

Destination Unreachable(3)은 코드로 이유를 구분해요.

| 코드 | 의미 |
|---|---|
| 0 | 네트워크 도달 불가(Network Unreachable) |
| 1 | 호스트 도달 불가(Host Unreachable) |
| 2 | 프로토콜 도달 불가(Protocol Unreachable) |
| 3 | 포트 도달 불가(Port Unreachable) |
| 4 | 단편화가 필요한데 DF가 설정됨(Fragmentation Needed) |
| 13 | 관리자에 의해 통신이 금지됨(필터링) |

Time Exceeded(11)는 코드 0이 "전송 중 TTL 만료", 코드 1이 "단편 재조립 시간 초과"예요.

**Redirect**(5)는 이런 상황에서 나와요. PC가 기본 게이트웨이 R1에게 패킷을 보냈는데, R1이 보니 같은 네트워크에 있는 R2로 보내는 게 더 빠른 길이에요. R1은 패킷을 R2로 넘겨주면서 PC에게 "다음부터는 이 목적지로 갈 때 R2로 바로 보내세요"라고 알려 줘요. 공격자가 가짜 Redirect로 경로를 바꿀 수 있어서 보안상 꺼 두는 경우가 많아요.

> [!NOTE]
> ICMP 오류 메시지 때문에 또 다른 ICMP 오류가 생기면 메시지가 끝없이 불어날 수 있어요. 그래서 **ICMP 오류 메시지에 대해서는 ICMP 오류를 보내지 않는** 등의 규칙이 있어요.

### ping의 원리

`ping`은 상대에게 **Echo Request**(유형 8)를 보내고 **Echo Reply**(유형 0)가 돌아오는지 확인해서, 상대에게 닿는지와 왕복 시간(RTT, Round Trip Time)을 알려 줘요.

```powershell
ping 192.0.2.10          # Windows: 기본 4번 보내고 끝
ping -t 192.0.2.10       # Ctrl+C를 누를 때까지 계속
ping -n 10 192.0.2.10    # 10번 보내기
ping -l 1000 192.0.2.10  # 데이터 크기를 1000바이트로
```

```bash
ping -c 4 192.0.2.10     # 리눅스: 4번 보내고 끝
```

리눅스의 `ping`은 `-c`로 횟수를 정하지 않으면 Ctrl+C를 누를 때까지 계속 보내요.

리눅스에서 실행하면 다음처럼 나와요.

```text
PING 192.0.2.10 (192.0.2.10) 56(84) bytes of data.
64 bytes from 192.0.2.10: icmp_seq=1 ttl=118 time=3.12 ms
64 bytes from 192.0.2.10: icmp_seq=2 ttl=118 time=3.05 ms
```

응답 줄의 `ttl`은 돌아온 Echo Reply 패킷에 남아 있던 TTL이고, `time`이 왕복 시간이에요.

> [!WARNING]
> ping이 실패한다고 상대가 꺼져 있다고 단정하면 안 돼요. 방화벽이 ICMP Echo Request를 막아 두는 경우가 많아요. Windows도 기본 방화벽 설정에서는 밖에서 들어오는 ping 요청에 응답하지 않는 경우가 많아요.

### traceroute의 원리

traceroute(Windows 명령은 `tracert`)는 목적지까지 거치는 라우터 목록을 보여 줘요. 비결은 **TTL을 일부러 작게** 설정하는 거예요.

1. TTL = 1로 보내요. 첫 번째 라우터가 TTL을 0으로 만들고 패킷을 버리면서 **Time Exceeded**(11)를 돌려줘요. 이 메시지의 출발지 주소가 첫 번째 라우터예요.
2. TTL = 2로 보내요. 이번에는 두 번째 라우터가 Time Exceeded를 보내요.
3. 이렇게 TTL을 1씩 늘리다가 목적지에 도착하면, 목적지가 보내는 응답으로 끝났음을 알아요.

```text
TTL=1  PC --> R1 (폐기)          R1 -> PC: Time Exceeded
TTL=2  PC --> R1 --> R2 (폐기)   R2 -> PC: Time Exceeded
TTL=3  PC --> R1 --> R2 --> 목적지  목적지 -> PC: 응답
```

마지막 응답의 종류는 도구마다 달라요.

| 도구 | 보내는 패킷 | 중간 라우터의 응답 | 목적지의 응답 |
|---|---|---|---|
| Windows `tracert` | ICMP Echo Request | Time Exceeded (11) | Echo Reply (0) |
| 리눅스 `traceroute` (기본) | 높은 번호 포트로 가는 UDP | Time Exceeded (11) | Port Unreachable (3, 코드 3) |

```powershell
tracert 192.0.2.10       # Windows
tracert -d 192.0.2.10    # 이름 해석을 생략해 더 빠르게
```

```bash
traceroute 192.0.2.10       # 리눅스(기본 UDP)
sudo traceroute -I 192.0.2.10  # ICMP Echo 방식(관리자 권한)
```

리눅스에 `traceroute`가 없으면 `sudo apt install traceroute` 또는 `sudo dnf install traceroute`로 설치해요. 결과에 `*`가 찍히면 그 단계에서 시간 안에 응답이 오지 않았다는 뜻이에요.

> [!EXAM]
> - ping = Echo Request(8) / Echo Reply(0)
> - traceroute = TTL을 늘려 가며 Time Exceeded(11)를 받는 방식
> - "TTL 초과 시 라우터가 보내는 메시지" → ICMP Time Exceeded
> - "더 좋은 경로를 알려 주는 메시지" → Redirect(5)
> - ICMP의 프로토콜 번호는 1, IGMP는 2

## IGMP — 멀티캐스트 그룹 관리

멀티캐스트(Multicast)는 같은 데이터를 원하는 여러 호스트에게 한 번에 보내는 방식이에요. 라우터 입장에서는 "우리 네트워크에 이 방송을 보고 싶은 호스트가 있나?"를 알아야 필요한 곳에만 데이터를 보낼 수 있어요. IGMP(Internet Group Management Protocol)는 **호스트와 같은 네트워크의 멀티캐스트 라우터** 사이에서 그룹 가입·탈퇴 정보를 주고받는 프로토콜이에요. 단체 채팅방에 들어가고 나가는 신청서라고 생각하면 돼요.

IGMP 메시지는 IP 패킷에 담기고 프로토콜 번호는 **2**예요. 멀티캐스트 주소(224.0.0.0–239.255.255.255)와 전송 방식은 [NAT와 전송 방식](/textbook/tcpip-nat-multicast)에서 자세히 배워요.

| 메시지 | 보내는 쪽 | 뜻 |
|---|---|---|
| Membership Query | 라우터 | "이 그룹을 받고 있는 호스트 있나요?" |
| Membership Report | 호스트 | "저 이 그룹에 가입할게요" 또는 "계속 받을게요" |
| Leave Group | 호스트 | "이제 그만 받을게요" (v2부터) |

| 버전 | 특징 |
|---|---|
| IGMPv1 | Query와 Report만 있어요. 탈퇴 메시지가 없어서 라우터는 한동안 Report가 없으면 탈퇴한 것으로 판단해요 |
| IGMPv2 | **Leave Group** 메시지와 특정 그룹만 묻는 질의가 추가되어 탈퇴가 빨라졌어요 |
| IGMPv3 | 특정 **출발지**(Source)만 골라 받거나 빼는 필터링이 추가되었어요 |

> [!NOTE]
> 스위치는 원래 멀티캐스트 프레임을 브로드캐스트처럼 모든 포트로 내보내요. **IGMP 스누핑**(IGMP Snooping)을 켜면 스위치가 오가는 IGMP 메시지를 엿들어, 그룹에 가입한 호스트가 연결된 포트로만 멀티캐스트를 보내요. 참고로 IPv6에서는 ARP 대신 ICMPv6의 이웃 탐색(ND), IGMP 대신 MLD가 같은 일을 해요.

## 핵심 정리

- ARP는 IPv4 주소로 MAC 주소를 알아낸다. 요청은 브로드캐스트, 응답은 유니캐스트다.
- 결과는 ARP 캐시에 저장된다(동적·정적). Windows는 `arp -a`, 리눅스는 `ip neigh`로 확인한다.
- 다른 네트워크로 갈 때는 기본 게이트웨이의 MAC을 ARP로 찾는다.
- 프록시 ARP는 라우터가 대신 응답, Gratuitous ARP는 자기 IP에 대한 ARP(충돌 감지·캐시 갱신)다.
- RARP는 MAC으로 자기 IP를 알아내는 옛 방식이며 BOOTP를 거쳐 DHCP로 대체되었다.
- ARP 스푸핑은 가짜 ARP 응답으로 캐시를 오염시키는 공격이다.
- ICMP(프로토콜 번호 1) 주요 유형: 0 Echo Reply, 3 Destination Unreachable, 5 Redirect, 8 Echo Request, 11 Time Exceeded.
- ping은 Echo Request/Reply, traceroute는 TTL을 1씩 늘리며 Time Exceeded를 받는다.
- IGMP(프로토콜 번호 2)는 호스트와 라우터 사이의 멀티캐스트 그룹 관리. v2에서 Leave Group, v3에서 출발지 필터링이 추가되었다.

## 스스로 확인하기

**1.** ARP 요청과 ARP 응답의 전송 방식을 바르게 짝지은 것은?
① 요청 유니캐스트, 응답 브로드캐스트 ② 요청 브로드캐스트, 응답 유니캐스트 ③ 요청과 응답 모두 브로드캐스트 ④ 요청과 응답 모두 멀티캐스트

> [!ANSWER]
> 정답: ②
> 누가 그 IP를 쓰는지 모르니 요청은 LAN 전체에 브로드캐스트하고, 응답은 요청한 호스트에게만 유니캐스트로 보내요.

**2.** 한빛상사 사무실 PC(192.168.0.25/24)가 외부 서버 198.51.100.20에 처음 접속하려 해요. 이때 PC가 ARP로 MAC 주소를 알아내야 하는 대상은?
① 외부 서버 ② 기본 게이트웨이 ③ DNS 서버 ④ 같은 네트워크의 모든 PC

> [!ANSWER]
> 정답: ②
> 목적지가 다른 네트워크에 있으면 프레임은 먼저 라우터로 가야 하므로, PC는 기본 게이트웨이의 MAC 주소를 ARP로 찾아요.

**3.** traceroute가 경로 위의 라우터 주소를 하나씩 알아낼 수 있는 것은 라우터가 어떤 ICMP 메시지를 돌려주기 때문인가요?
① Echo Reply(0) ② Redirect(5) ③ Time Exceeded(11) ④ Parameter Problem(12)

> [!ANSWER]
> 정답: ③
> TTL이 0이 된 라우터는 패킷을 버리고 Time Exceeded를 보내요. 이 메시지의 출발지 주소가 곧 그 라우터의 주소예요.

**4.** `arp -a`로 확인해 보니 게이트웨이 192.168.0.1과 다른 PC 192.168.0.77의 MAC 주소가 똑같이 나왔어요. 가장 먼저 의심할 공격은?
① SYN 플러딩 ② ARP 스푸핑 ③ DNS 캐시 포이즈닝 ④ 포트 스캔

> [!ANSWER]
> 정답: ②
> 공격자가 가짜 ARP 응답으로 게이트웨이 IP를 자기 MAC에 연결해 두면 이런 결과가 나와요. 전형적인 ARP 스푸핑의 흔적이에요.

**5.** IGMP 버전 2에서 새로 추가되어 호스트가 그룹을 빨리 떠날 수 있게 해 준 메시지는?
① Membership Query ② Membership Report ③ Leave Group ④ Echo Request

> [!ANSWER]
> 정답: ③
> IGMPv1에는 탈퇴 메시지가 없어 시간이 지나야 탈퇴로 처리됐어요. v2부터 Leave Group 메시지로 탈퇴를 바로 알릴 수 있어요.
