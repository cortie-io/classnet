사람은 `www.example.com` 같은 이름을 기억하기 쉽지만, 컴퓨터가 통신하려면 IP 주소가 필요해요. 또 새 노트북을 회사 네트워크에 연결하면 IP 주소, 게이트웨이, DNS 서버 주소가 알아서 설정되죠. 이 단원에서는 이름을 주소로 바꿔 주는 DNS와, 주소 설정을 자동으로 나눠 주는 DHCP를 배워요. 둘 다 거의 모든 네트워크에서 쓰이고, 레코드 종류와 DHCP 동작 순서는 시험에 자주 나와요.

> [!GOAL]
> - 도메인 이름의 계층 구조와 FQDN을 설명할 수 있다.
> - 재귀 질의와 반복 질의, DNS 캐시와 TTL의 관계를 이해한다.
> - 주요 DNS 레코드와 정방향·역방향 조회를 구분할 수 있다.
> - DHCP의 DORA 과정, 임대 갱신 시점, 릴레이 에이전트의 역할을 말할 수 있다.

## DNS — 이름을 주소로

### DNS가 필요한 이유

인터넷 초기에는 모든 컴퓨터의 이름과 주소를 적은 파일 하나를 나눠 받아 썼어요. 컴퓨터가 늘어나자 파일 하나로는 감당할 수 없었고, 그래서 이름 정보를 여러 서버에 **나누어 계층적으로** 관리하는 DNS(Domain Name System)가 만들어졌어요. DNS는 전 세계에 흩어진 거대한 전화번호부라고 생각하면 돼요. DNS는 **53번 포트**를 쓰고, 보통 질의는 UDP, 영역 전송처럼 큰 데이터는 TCP로 주고받아요.

### 도메인 이름의 계층 구조

도메인 이름은 뒤집힌 나무 모양이에요. 맨 위가 루트이고, 오른쪽에서 왼쪽으로 읽을수록 아래 단계로 내려가요.

```text
                    . (root)
        +-----------+-----------+
       com         org          kr
        |           |           |
     example     example        co
        |           |
   +----+----+     www
  www      mail
```

| 단계 | 예 | 설명 |
|---|---|---|
| 루트(Root) | `.` | 맨 꼭대기. 루트 서버는 13개의 이름(A–M)으로 운영되고, 실제로는 애니캐스트로 전 세계에 많은 서버가 있어요 |
| 최상위 도메인(TLD, Top-Level Domain) | `com`, `org`, `kr` | 일반 도메인(gTLD: com, net, org 등)과 국가 코드 도메인(ccTLD: kr, jp 등) |
| 2단계 도메인(SLD, Second-Level Domain) | `example.com`의 `example` | 기관·회사가 등록해 쓰는 이름. kr 아래에서는 `co.kr`(기업), `ac.kr`(대학), `go.kr`(정부)처럼 분류가 한 단계 더 들어가요 |
| 하위 도메인·호스트 | `www`, `mail` | 도메인 주인이 자유롭게 만드는 이름 |

**FQDN**(Fully Qualified Domain Name, 정규화된 도메인 이름)은 호스트 이름부터 루트까지 빠짐없이 적은 전체 이름이에요. 예를 들어 `www.example.com.`이고, 맨 끝의 점이 루트를 뜻해요. 평소에는 이 점을 생략해서 써요. 점으로 나뉜 각 부분을 레이블(Label)이라고 하고, 레이블 하나는 최대 63자예요.

### 이름 해석에 참여하는 셋

| 구성 요소 | 하는 일 |
|---|---|
| 리졸버(Resolver) | PC 안에서 DNS 질의를 만들어 보내는 부분 |
| 로컬 DNS 서버(재귀 확인자) | 통신사나 회사가 운영하는 DNS 서버. PC 대신 답을 찾아 주고 결과를 캐시에 저장 |
| 권한 있는 네임 서버(Authoritative Name Server) | 특정 도메인(영역)의 레코드 원본을 가진 서버 |

### 재귀 질의와 반복 질의

민수의 PC가 `www.example.com`의 주소를 처음 찾는 과정이에요.

```text
         (1) 재귀 질의              (2)(3)(4) 반복 질의
 [PC] ---------------> [로컬 DNS] -----> [루트 서버]
      <---------------             -----> [com 서버]
         (5) 최종 답               -----> [example.com 서버]
```

1. PC가 로컬 DNS 서버에 "`www.example.com`의 주소를 **최종 답으로** 알려 주세요"라고 물어요. 이것이 **재귀 질의**(Recursive Query)예요.
2. 로컬 DNS 서버가 루트 서버에 물으면, 루트 서버는 "com은 저 서버가 담당해요"라고 다음 서버를 알려 줘요(위임, Referral).
3. com 서버에 물으면 "example.com은 저 서버가 담당해요"라고 알려 줘요.
4. example.com의 권한 있는 네임 서버가 "203.0.113.80이에요"라고 최종 답을 줘요.
5. 로컬 DNS 서버는 답을 캐시에 저장하고 PC에 전달해요.

2–4번처럼 "모르면 다음 서버를 알려 주고, 묻는 쪽이 직접 차례로 찾아가는" 방식이 **반복 질의**(Iterative Query)예요. 재귀 질의는 비서에게 "알아서 찾아와 줘"라고 맡기는 것, 반복 질의는 안내 창구를 돌며 "다음 창구로 가세요"라는 안내를 받는 것에 비유할 수 있어요.

> [!EXAM]
> 보통 **PC → 로컬 DNS 서버는 재귀 질의**, **로컬 DNS 서버 → 루트·TLD·권한 서버는 반복 질의**예요. 두 이름을 바꿔 놓은 보기가 자주 나와요.

### 캐시와 TTL

로컬 DNS 서버와 PC는 한 번 얻은 답을 **캐시**(Cache)에 저장해 두고, 같은 질문이 오면 바로 답해요. 얼마나 오래 저장할지는 레코드마다 정해진 **TTL**(Time To Live, 초 단위)이 결정해요. TTL이 3600이면 1시간 동안 캐시를 써요. 캐시 덕분에 빠르고 서버 부담도 줄지만, 레코드를 바꿔도 TTL이 끝날 때까지는 옛 주소가 쓰일 수 있어요.

Windows에서는 PC의 DNS 캐시를 보고 비울 수 있어요.

```powershell
ipconfig /displaydns    # DNS 캐시 내용 보기
ipconfig /flushdns      # DNS 캐시 비우기
```

> [!NOTE]
> IP 헤더의 TTL은 "거칠 수 있는 라우터 수"이고, DNS 레코드의 TTL은 "캐시에 보관할 시간(초)"이에요. 이름만 같고 뜻은 달라요.

### hosts 파일

DNS 서버에 묻기 전에 컴퓨터 안의 **hosts 파일**을 먼저 확인하는 것이 일반적이에요. 이 파일에 적힌 이름은 DNS보다 우선해서 쓰여요.

- Windows: `C:\Windows\System32\drivers\etc\hosts`
- 리눅스: `/etc/hosts` (확인 순서는 `/etc/nsswitch.conf`의 `hosts:` 줄, DNS 서버 주소는 `/etc/resolv.conf`에서 정해요)

```text
192.168.0.10    intranet.example.com
```

테스트할 때 편리하지만, 악성 프로그램이 hosts 파일을 고쳐 가짜 사이트로 유도하는 경우도 있으니 주의해야 해요.

## DNS 레코드

도메인 하나를 관리하는 범위를 **영역**(Zone)이라고 하고, 영역 안의 정보 한 줄 한 줄을 **리소스 레코드**(Resource Record)라고 해요.

```text
example.com.        IN  NS     ns1.example.com.
example.com.        IN  MX 10  mail.example.com.
ns1.example.com.    IN  A      203.0.113.53
www.example.com.    IN  A      203.0.113.80
www.example.com.    IN  AAAA   2001:db8::80
mail.example.com.   IN  A      203.0.113.25
ftp.example.com.    IN  CNAME  www.example.com.
```

| 레코드 | 하는 일 | 예 |
|---|---|---|
| A | 이름 → IPv4 주소 | www → 203.0.113.80 |
| AAAA | 이름 → IPv6 주소 | www → 2001:db8::80 |
| CNAME | 별칭(Canonical Name). 다른 이름을 가리킴 | ftp는 www의 별칭 |
| MX | 이 도메인의 메일을 받을 서버. 우선순위 숫자가 **작을수록 먼저** 사용 | MX 10 mail.example.com. |
| NS | 이 영역을 담당하는 네임 서버 | ns1.example.com. |
| PTR | IP 주소 → 이름(역방향 조회) | 203.0.113.80 → `www.example.com.` |
| SOA | 영역의 시작과 기본 정보 | 아래 설명 |
| TXT | 자유로운 텍스트. 메일 발신 정책(SPF), 도메인 소유 확인 등에 사용 | "v=spf1 mx -all" |
| SRV | 특정 서비스를 제공하는 서버의 이름, 포트, 우선순위 | Active Directory가 도메인 컨트롤러를 찾을 때 사용 |

**SOA(Start of Authority)** 레코드는 영역마다 하나 있고, 주 네임 서버, 관리자 메일 주소, 일련번호(Serial), 보조 서버의 갱신 주기(Refresh), 재시도 간격(Retry), 만료 시간(Expire), 최소 TTL(Minimum) 같은 값을 담아요. 관리자 메일은 `@` 대신 점으로 적어서 `admin.example.com.`이 `admin@example.com`을 뜻해요.

> [!WARNING]
> MX와 CNAME은 IP 주소가 아니라 **이름**을 가리켜요. 메일 서버의 실제 주소는 그 이름의 A(또는 AAAA) 레코드에서 다시 찾아요.

### 정방향 조회와 역방향 조회

- **정방향 조회 영역(Forward Lookup Zone)**: 이름 → IP 주소. A, AAAA 레코드가 들어 있어요.
- **역방향 조회 영역(Reverse Lookup Zone)**: IP 주소 → 이름. PTR 레코드가 들어 있어요.

역방향 조회에는 특별한 도메인 `in-addr.arpa`를 쓰고, IP 주소의 옥텟을 **거꾸로** 적어요. 이름은 오른쪽으로 갈수록 큰 단위인데, IP 주소는 왼쪽이 큰 단위라서 순서를 뒤집는 거예요.

| IP 주소 | 역방향 조회 이름 |
|---|---|
| 203.0.113.80 | `80.113.0.203.in-addr.arpa` |
| 203.0.113.0/24 네트워크의 영역 이름 | `113.0.203.in-addr.arpa` |

IPv6의 역방향 조회는 `ip6.arpa`를 써요. 역방향 조회는 메일 서버가 보낸 쪽의 신원을 확인하거나, 로그에 IP 대신 이름을 보여 줄 때 쓰여요.

### 주 영역과 보조 영역

영역 원본을 가진 **주(Primary) 서버**의 내용을 **보조(Secondary) 서버**가 복사해 가는 것을 **영역 전송**(Zone Transfer)이라고 해요. 전체를 복사하는 AXFR과 바뀐 부분만 받는 IXFR이 있고, **TCP 53번**을 써요. 보조 서버를 두면 주 서버가 멈춰도 이름 해석이 계속돼요. Windows Server의 DNS 영역 설정은 [Windows 네트워크 서비스](/textbook/nos-windows-network-services)에서 다뤄요.

### 확인 명령

```powershell
nslookup www.example.com          # A 레코드 조회
nslookup -type=mx example.com     # MX 레코드 조회
nslookup 203.0.113.80             # 역방향 조회
```

```bash
dig www.example.com               # 자세한 조회 결과
dig example.com MX                # MX 레코드
dig -x 203.0.113.80               # 역방향 조회
```

`nslookup`은 Windows와 리눅스 모두에 있어요. 리눅스에서 `dig`가 없으면 `sudo dnf install bind-utils` 또는 `sudo apt install dnsutils`로 설치해요.

## DHCP — 주소 설정을 자동으로

### DHCP가 하는 일

DHCP(Dynamic Host Configuration Protocol)는 네트워크에 들어온 호스트에게 **IP 주소, 서브넷 마스크, 기본 게이트웨이, DNS 서버 주소** 등을 자동으로 빌려주는 프로토콜이에요. 관리자가 PC마다 손으로 설정할 필요가 없고, 주소가 겹치는 실수도 줄어요. **UDP를 쓰며 서버는 67번, 클라이언트는 68번** 포트예요. RARP의 한계를 보완한 BOOTP를 발전시킨 것이 DHCP예요([ARP·ICMP·IGMP](/textbook/tcpip-arp-icmp) 참고).

### 주소를 받는 4단계 — DORA

| 단계 | 메시지 | 방향 | 전송 방식 | 내용 |
|---|---|---|---|---|
| 1 | DHCPDISCOVER | 클라이언트 → 네트워크 전체 | **브로드캐스트** | "DHCP 서버 계세요?" |
| 2 | DHCPOFFER | 서버 → 클라이언트 | 브로드캐스트 또는 유니캐스트 | "192.168.0.101을 쓰세요. 마스크·게이트웨이·DNS·임대 기간은 이래요" |
| 3 | DHCPREQUEST | 클라이언트 → 네트워크 전체 | **브로드캐스트** | "그 제안을 받을게요" |
| 4 | DHCPACK | 서버 → 클라이언트 | 브로드캐스트 또는 유니캐스트 | "확정이에요. 이제 쓰세요" |

머리글자를 따서 **DORA**라고 외워요.

- **Discover**는 아직 IP 주소도 없고 서버 주소도 모르니, 출발지 `0.0.0.0:68`에서 목적지 `255.255.255.255:67`로 브로드캐스트해요.
- **Offer**와 **Ack**는 클라이언트에게 아직 IP가 없어서, 클라이언트의 요청 방식에 따라 브로드캐스트로 보내거나 MAC 주소를 이용해 유니캐스트로 보내요.
- **Request**도 브로드캐스트예요. 서버 여러 대가 제안했을 수 있으니, "저는 이 서버의 제안을 골랐어요"라고 모두에게 알려야 선택받지 못한 서버들이 제안한 주소를 거둬들일 수 있어요.

그 밖의 메시지도 알아 두세요.

| 메시지 | 뜻 |
|---|---|
| DHCPNAK | 서버가 요청을 거절함(예: 다른 네트워크로 옮겨 와 예전 주소를 요청할 때) |
| DHCPDECLINE | 받은 주소를 이미 다른 장비가 쓰고 있어 클라이언트가 거절함 |
| DHCPRELEASE | 클라이언트가 주소를 반납함 |
| DHCPINFORM | 주소는 이미 있고 다른 설정 정보만 요청함 |

### 임대와 갱신

DHCP 주소는 주는 것이 아니라 **빌려주는(임대, Lease)** 거예요. 임대 기간이 8일이라면 이렇게 진행돼요.

| 시점 | 이름 | 클라이언트의 행동 |
|---|---|---|
| 50% (4일째) | T1, 갱신(Renewing) | 주소를 준 **원래 서버에 유니캐스트**로 DHCPREQUEST를 보내 연장 요청. ACK를 받으면 임대 기간이 처음부터 다시 시작 |
| 87.5% (7일째) | T2, 재바인딩(Rebinding) | 원래 서버가 답이 없으면 **아무 서버에게나 브로드캐스트**로 DHCPREQUEST |
| 100% (8일째) | 임대 만료 | 주소 사용을 멈추고 DHCPDISCOVER부터 다시 시작 |

> [!NOTE]
> Windows는 DHCP 서버를 끝내 찾지 못하면 169.254.0.0/16 대역에서 스스로 주소를 정해요. 이것을 APIPA(Automatic Private IP Addressing)라고 해요. PC 주소가 169.254로 시작한다면 "DHCP 서버에서 주소를 받지 못했다"는 신호예요([IPv4 주소 체계](/textbook/tcpip-ipv4-address) 참고).

Windows에서 DHCP 임대 상태를 확인하고 다시 받는 명령이에요.

```powershell
ipconfig /all       # DHCP 서버, 임대·만료 시각 확인
ipconfig /release   # 주소 반납(DHCPRELEASE)
ipconfig /renew     # 주소 새로 요청
```

### DHCP 릴레이 에이전트

Discover는 브로드캐스트인데 **라우터는 브로드캐스트를 다른 네트워크로 넘기지 않아요.** 그렇다고 서브넷마다 DHCP 서버를 둘 수는 없죠. 이때 라우터(또는 L3 스위치)에 **DHCP 릴레이 에이전트(DHCP Relay Agent)** 기능을 켜요.

```text
 [PC] --브로드캐스트--> [라우터] --유니캐스트--> [DHCP 서버]
 192.168.20.0/24      (릴레이)                 10.0.0.5
```

릴레이 에이전트는 클라이언트의 브로드캐스트를 받아 DHCP 서버에 **유니캐스트로 전달**해요. 이때 요청을 받은 인터페이스의 주소(위 예에서는 192.168.20.1)를 메시지 안의 **giaddr(Gateway IP Address)** 필드에 적어 보내요. 서버는 이 값을 보고 192.168.20.0/24용 주소 풀에서 주소를 골라 줘요. 시스코 IOS 계열 예시는 다음과 같아요.

```text
interface GigabitEthernet0/1
 ip address 192.168.20.1 255.255.255.0
 ip helper-address 10.0.0.5
```

### DHCP 서버에서 정하는 것

| 설정 | 뜻 |
|---|---|
| 범위(Scope) | 나눠 줄 주소 묶음. 예: 192.168.0.100–192.168.0.200 |
| 제외 범위(Exclusion) | 범위 안에서 나눠 주지 않을 주소(서버·프린터에 직접 지정한 주소 등) |
| 예약(Reservation) | 특정 MAC 주소에는 항상 같은 IP를 줌 |
| 임대 기간 | 주소를 빌려주는 기간 |
| 옵션(Option) | 주소 외에 함께 알려 줄 설정 |

| 옵션 번호 | 내용 |
|---|---|
| 1 | 서브넷 마스크 |
| 3 | 라우터(기본 게이트웨이) |
| 6 | DNS 서버 |
| 15 | 도메인 이름 |
| 51 | 임대 기간 |
| 53 | DHCP 메시지 종류(Discover, Offer 등) |
| 66, 67 | 네트워크 부팅용 TFTP 서버 이름, 부팅 파일 이름 |

> [!WARNING]
> 누군가 몰래 연결한 가짜 DHCP 서버(Rogue DHCP)가 엉뚱한 게이트웨이나 DNS를 나눠 주면 트래픽이 공격자에게 흘러갈 수 있어요. 스위치의 DHCP 스누핑(DHCP Snooping)은 허락된 포트에서 온 DHCP 응답만 통과시켜 이를 막아요.

> [!EXAM]
> - DHCP 포트: 서버 **UDP 67**, 클라이언트 **UDP 68**
> - 순서: Discover → Offer → Request → Ack. Discover와 Request는 브로드캐스트
> - 갱신: T1 = 임대 기간의 50%(원래 서버에 유니캐스트), T2 = 87.5%(브로드캐스트)
> - 다른 서브넷의 DHCP 서버를 쓰려면 릴레이 에이전트(시스코 IOS의 `ip helper-address`)

## 핵심 정리

- DNS는 이름과 IP 주소를 바꿔 주는 분산·계층형 시스템이며 53번 포트(질의는 주로 UDP, 영역 전송은 TCP)를 쓴다.
- 계층: 루트(.) → TLD(com, kr 등) → SLD(example) → 호스트(www). 끝까지 다 적은 이름이 FQDN.
- PC → 로컬 DNS는 재귀 질의, 로컬 DNS → 루트·TLD·권한 서버는 반복 질의. 결과는 TTL 동안 캐시된다.
- 레코드: A(IPv4), AAAA(IPv6), CNAME(별칭), MX(메일 서버), NS(네임 서버), PTR(역방향), SOA(영역 정보), TXT(텍스트), SRV(서비스 위치).
- 역방향 조회는 옥텟을 거꾸로 적은 `in-addr.arpa` 이름으로 PTR 레코드를 찾는다.
- hosts 파일은 DNS보다 먼저 확인되는 로컬 이름표다.
- DHCP는 UDP 67(서버)·68(클라이언트)을 쓰고, DORA(Discover → Offer → Request → Ack) 순서로 주소를 임대한다.
- 임대 갱신은 T1(50%)에 원래 서버로 유니캐스트, T2(87.5%)에 브로드캐스트.
- 라우터는 브로드캐스트를 넘기지 않으므로 다른 네트워크의 DHCP 서버를 쓰려면 릴레이 에이전트가 필요하다.

## 스스로 확인하기

**1.** 도메인으로 오는 메일을 받을 서버를 지정하는 DNS 레코드는?

> [!ANSWER]
> 정답: ③
> MX(Mail Exchanger) 레코드가 메일 서버를 지정하고, 우선순위 숫자가 작은 서버부터 사용해요.

**2.** 로컬 DNS 서버가 루트 서버, TLD 서버, 권한 있는 네임 서버에 차례로 물으며 "다음엔 이 서버에 물어보세요"라는 안내를 받는 질의 방식은?
① 재귀 질의 ② 반복 질의 ③ 역방향 질의 ④ 영역 전송

> [!ANSWER]
> 정답: ②
> 묻는 쪽이 안내받은 서버를 직접 차례로 찾아가는 방식이 반복 질의예요. PC가 로컬 DNS 서버에 최종 답을 맡기는 것은 재귀 질의예요.

**3.** 198.51.100.25에 해당하는 이름을 PTR 레코드로 찾을 때 실제로 조회하는 이름은?
① `198.51.100.25.in-addr.arpa` ② `25.100.51.198.in-addr.arpa` ③ `25.100.51.198.ip6.arpa` ④ `198.51.100.in-addr.arpa`

> [!ANSWER]
> 정답: ②
> IPv4 역방향 조회는 옥텟 순서를 뒤집어 `in-addr.arpa` 앞에 붙여요. `ip6.arpa`는 IPv6용이에요.

**4.** 임대 기간이 10일인 DHCP 클라이언트가 처음으로 임대 연장을 시도하는 시점과 방법으로 옳은 것은?
① 5일째, 원래 서버에 유니캐스트로 요청 ② 5일째, 브로드캐스트로 Discover ③ 8.75일째, 원래 서버에 유니캐스트로 요청 ④ 10일째, 브로드캐스트로 Discover

> [!ANSWER]
> 정답: ①
> 임대 기간의 50%인 T1(5일째)에 원래 서버에 유니캐스트로 DHCPREQUEST를 보내요. 87.5%인 T2(8.75일째)에는 브로드캐스트로 요청해요.

**5.** 한빛상사는 DHCP 서버 한 대를 본사 서버실에 두고, 라우터 너머 여러 층의 PC에도 주소를 나눠 주려고 해요. 라우터에 필요한 기능은?
① NAT ② 프록시 ARP ③ DHCP 릴레이 에이전트 ④ APIPA

> [!ANSWER]
