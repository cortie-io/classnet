IP는 최선을 다해 배달할 뿐, 패킷이 사라지거나 순서가 뒤섞여도 책임지지 않아요. 그 위에서 "보낸 데이터가 빠짐없이, 순서대로 도착한다"를 보장하는 것이 TCP예요. 이 단원에서는 TCP가 연결을 맺고 끊는 과정, 바이트마다 번호를 매겨 확인하는 방법, 받는 쪽과 네트워크가 감당할 만큼만 보내도록 속도를 조절하는 방법을 차례로 배워요. 웹, 메일, 파일 전송처럼 데이터가 하나라도 빠지면 안 되는 서비스는 거의 다 TCP 위에서 동작해요.

> [!GOAL]
> - TCP의 특징과 헤더 필드, 플래그의 역할을 설명할 수 있다.
> - 3-way 핸드셰이크와 4-way 종료 과정을 순서 번호와 함께 따라갈 수 있다.
> - 순서 번호와 확인 응답 번호를 계산할 수 있다.
> - 흐름 제어와 혼잡 제어(느린 시작, 혼잡 회피, 빠른 재전송·회복)를 구분할 수 있다.

## TCP는 어떤 프로토콜인가

TCP(Transmission Control Protocol)는 전송 계층(OSI 4계층) 프로토콜이고, IP 헤더의 프로토콜 번호는 6이에요. TCP가 다루는 데이터 단위를 **세그먼트**(Segment)라고 불러요.

전화 통화를 떠올리면 TCP의 성격이 잘 보여요. 먼저 "여보세요?" "네, 들려요"로 연결을 확인하고, 중간에 "방금 말한 거 들었어?"라고 확인하며, 끝날 때는 서로 인사하고 끊죠.

| 특징 | 뜻 |
|---|---|
| 연결 지향(Connection-oriented) | 데이터를 보내기 전에 연결을 맺고, 다 쓰면 끊어요 |
| 신뢰성(Reliability) | 확인 응답(ACK)을 받고, 못 받으면 다시 보내요(재전송) |
| 순서 보장 | 순서 번호로 뒤섞인 세그먼트를 바로잡고 중복을 버려요 |
| 바이트 스트림(Byte Stream) | 데이터를 메시지 단위가 아니라 이어진 바이트 흐름으로 다뤄요 |
| 전이중(Full Duplex) | 한 연결에서 양쪽이 동시에 보내고 받을 수 있어요 |
| 흐름 제어·혼잡 제어 | 받는 쪽과 네트워크 상황에 맞춰 보내는 양을 조절해요 |
| 1:1 통신 | 유니캐스트만 가능하고 브로드캐스트·멀티캐스트는 못 해요 |

## TCP 헤더

TCP 헤더도 IP 헤더처럼 옵션 없이 **20바이트**, 옵션을 포함하면 최대 **60바이트**예요.

```text
0           8           16          24          31
+-----------------------+-----------------------+
|      Source Port      |   Destination Port    |
+-----------------------+-----------------------+
|                Sequence Number                |
+-----------------------------------------------+
|             Acknowledgment Number             |
+-----+-----+-----------+-----------------------+
|Offs.|Rsvd.|   Flags   |        Window         |
+-----+-----+-----------+-----------------------+
|       Checksum        |    Urgent Pointer     |
+-----------------------+-----------------------+
|          Options + Padding (variable)         |
+-----------------------------------------------+
```

| 필드 | 크기 | 하는 일 |
|---|---|---|
| 출발지 포트(Source Port) | 16비트 | 보내는 프로그램의 포트 번호 |
| 목적지 포트(Destination Port) | 16비트 | 받을 프로그램의 포트 번호 |
| 순서 번호(Sequence Number) | 32비트 | 이 세그먼트에 담긴 데이터의 첫 바이트 번호 |
| 확인 응답 번호(Acknowledgment Number) | 32비트 | 다음에 받기를 기대하는 바이트 번호 |
| 데이터 오프셋(Data Offset) | 4비트 | 헤더 길이를 4바이트 단위로 표시(IP의 IHL과 같은 방식) |
| 예약(Reserved) | 4비트 | 나중을 위해 비워 둔 자리 |
| 플래그(Flags) | 8비트 | 연결 제어용 비트들(아래 표) |
| 윈도 크기(Window) | 16비트 | 받는 쪽이 지금 더 받을 수 있는 바이트 수 |
| 체크섬(Checksum) | 16비트 | 헤더와 데이터 전체의 오류 검사 |
| 긴급 포인터(Urgent Pointer) | 16비트 | URG가 1일 때 긴급 데이터가 끝나는 위치 |
| 옵션(Options) | 가변 | MSS, 윈도 확장, SACK, 타임스탬프 등 |

> [!NOTE]
> 처음 규격에서는 예약 6비트, 플래그 6비트(URG·ACK·PSH·RST·SYN·FIN)였어요. 나중에 혼잡 알림용 ECE·CWR이 예약 자리 일부를 가져가서 지금은 예약 4비트, 플래그 8비트로 봐요. 시험 문제가 "플래그 6비트"라고 하면 처음 규격 기준이에요.

몇 가지 필드를 더 짚어 볼게요.

- **체크섬**: IP 헤더 체크섬과 달리 **데이터까지** 검사해요. 계산할 때 출발지·목적지 IP 주소 등을 담은 가상 헤더(Pseudo Header)도 함께 넣어요.
- **윈도 크기**: 16비트라 최대 65,535바이트예요. 빠른 회선에서는 부족해서, 연결할 때 윈도 확장(Window Scale) 옵션으로 더 크게 쓸 수 있어요.
- **MSS(Maximum Segment Size)**: 세그먼트 하나에 담을 수 있는 데이터의 최대 크기로, 연결을 맺을 때 옵션으로 알려 줘요. 이더넷에서는 보통 1,500(MTU) − 20(IP 헤더) − 20(TCP 헤더) = **1,460바이트**예요.

### 플래그(제어 비트)

| 플래그 | 원래 이름 | 1일 때의 뜻 |
|---|---|---|
| URG | Urgent | 긴급 포인터 필드가 유효함 |
| ACK | Acknowledgment | 확인 응답 번호가 유효함. 연결이 맺어진 뒤에는 거의 모든 세그먼트에서 1 |
| PSH | Push | 버퍼에 모아 두지 말고 바로 응용 프로그램에 넘겨 달라 |
| RST | Reset | 연결을 즉시 강제로 끊음. 닫힌 포트로 연결 요청이 오면 RST로 거절 |
| SYN | Synchronize | 연결 시작. 서로의 시작 순서 번호를 맞춤 |
| FIN | Finish | 보낼 데이터를 다 보냈으니 연결을 끝내자 |
| ECE | ECN-Echo | 네트워크에서 혼잡 표시를 받았음을 상대에게 알림 |
| CWR | Congestion Window Reduced | 혼잡 알림을 받고 전송량을 줄였음을 알림 |

> [!TIP]
> 기본 6개 플래그는 헤더 안의 순서대로 **U-A-P-R-S-F**예요. "**우아**(U·A)한 **파리**(P·R) **산**(S)책 **풍**(F)경"처럼 문장으로 묶어 두면 순서 문제에 대비할 수 있어요.

## 연결 설정 — 3-way 핸드셰이크

TCP는 데이터를 보내기 전에 세그먼트 세 개를 주고받아 연결을 맺어요. 이것을 **3-way 핸드셰이크**(3-way Handshake)라고 해요. 이 과정에서 양쪽은 서로의 **초기 순서 번호**(ISN, Initial Sequence Number)를 알게 되고, 연결 중에 쓸 MSS 같은 옵션도 맞춰요.

민수의 PC(클라이언트)가 웹 서버의 80번 포트에 접속하는 예로 볼게요. 클라이언트의 ISN은 1000, 서버의 ISN은 5000이라고 할게요.

```text
   클라이언트                            서버
   CLOSED                             LISTEN
      |--(1) SYN seq=1000 -------------->|
   SYN_SENT                              |
      |<-(2) SYN+ACK seq=5000 ack=1001 --|
      |                            SYN_RECEIVED
      |--(3) ACK seq=1001 ack=5001 ----->|
   ESTABLISHED                     ESTABLISHED
```

1. **SYN**: 클라이언트가 "연결하고 싶어요. 제 순서 번호는 1000부터예요"라고 보내요.
2. **SYN+ACK**: 서버가 "좋아요(ACK). 1001번부터 받을게요(ack=1001). 제 순서 번호는 5000부터예요(SYN)"라고 답해요.
3. **ACK**: 클라이언트가 "5001번부터 받을게요(ack=5001)"라고 확인하면 양쪽 모두 연결 완료(ESTABLISHED) 상태가 돼요.

> [!WARNING]
> 데이터가 없는데도 ack가 1001인 이유는 **SYN과 FIN은 데이터 1바이트처럼 순서 번호를 하나 차지**하기 때문이에요. 반면 데이터 없이 ACK만 보내는 세그먼트는 순서 번호를 쓰지 않아요. 그래서 (3)의 다음 데이터도 seq=1001에서 시작해요.

ISN은 매번 0이 아니라 예측하기 어려운 값으로 정해요. 번호를 쉽게 맞힐 수 있으면 공격자가 남의 연결에 가짜 세그먼트를 끼워 넣을 수 있기 때문이에요.

> [!EXAM]
> **SYN 플러딩**(SYN Flooding)은 공격자가 가짜 출발지 주소로 SYN만 잔뜩 보내고 세 번째 ACK를 보내지 않는 공격이에요. 서버는 `SYN_RECEIVED` 상태의 반쯤 열린 연결(Half-open Connection)을 쌓아 두다가 대기열이 꽉 차서 정상 사용자를 받지 못해요. 3-way 핸드셰이크의 약점을 노린 서비스 거부 공격으로 자주 출제돼요. 자세한 내용은 [네트워크 보안 기초](/textbook/tcpip-security-protocols)에서 다뤄요.

## 데이터 전송 — 순서 번호와 확인 응답

TCP의 순서 번호는 세그먼트가 아니라 **바이트**에 붙는 번호예요. 세그먼트 헤더의 순서 번호는 그 세그먼트에 담긴 첫 바이트의 번호이고, 확인 응답 번호는 "여기 바로 앞까지는 다 받았으니 **다음엔 이 번호부터** 보내 주세요"라는 뜻이에요.

- 다음 순서 번호 = 이번 순서 번호 + 데이터 길이
- 확인 응답 번호 = 받은 순서 번호 + 받은 데이터 길이

### 단계별 예제

앞의 핸드셰이크에 이어서 데이터를 주고받아요. 클라이언트는 seq=1001부터, 서버는 seq=5001부터 시작해요.

| 차례 | 방향 | seq | 데이터 | ack | 설명 |
|---|---|---|---|---|---|
| 1 | 클라이언트 → 서버 | 1001 | 500바이트 | 5001 | 1001–1500번 바이트를 보냄 |
| 2 | 서버 → 클라이언트 | 5001 | 없음 | 1501 | "1500번까지 받았어요, 1501번부터 주세요" |
| 3 | 클라이언트 → 서버 | 1501 | 300바이트 | 5001 | 1501–1800번 바이트 |
| 4 | 서버 → 클라이언트 | 5001 | 200바이트 | 1801 | 응답 데이터와 확인 응답을 함께 보냄 |
| 5 | 클라이언트 → 서버 | 1801 | 없음 | 5201 | 서버의 5001–5200번 바이트를 잘 받음 |

4번처럼 상대에게 보낼 데이터에 확인 응답을 얹어 함께 보내는 것을 **피기배킹**(Piggybacking)이라고 해요. 세그먼트 수를 줄여 효율이 좋아져요.

### 세그먼트가 사라지면

3번 세그먼트(1501–1800)가 중간에 사라지고 그다음 세그먼트(1801–2100)가 먼저 도착했다고 해 봐요. 서버는 1501번이 비어 있으니 계속 ack=1501을 보내요. 같은 확인 응답 번호가 반복되는 이것을 **중복 ACK**(Duplicate ACK)라고 해요. 클라이언트는 다음 두 경우에 1501번부터 다시 보내요.

- 재전송 타이머(RTO, Retransmission Timeout)가 끝날 때까지 ACK가 오지 않을 때
- 중복 ACK를 **3번** 더 받았을 때(빠른 재전송, 아래 혼잡 제어에서 다시 나와요)

## 연결 종료 — 4-way 핸드셰이크

연결을 끊을 때는 양쪽이 각자 "나는 다 보냈어"라고 FIN을 보내고 상대가 ACK로 확인해요. 방향마다 따로 닫기 때문에 세그먼트가 네 개 필요해요. 위 예제가 끝난 뒤 클라이언트(seq=1801)가 먼저 종료를 시작한다고 할게요.

```text
   클라이언트                            서버
   ESTABLISHED                    ESTABLISHED
      |--(1) FIN seq=1801 ack=5201 ----->|
   FIN_WAIT_1                       CLOSE_WAIT
      |<-(2) ACK seq=5201 ack=1802 ------|
   FIN_WAIT_2          (남은 데이터 전송 가능)
      |<-(3) FIN seq=5201 ack=1802 ------|
      |                              LAST_ACK
      |--(4) ACK seq=1802 ack=5202 ----->|
   TIME_WAIT                          CLOSED
      | (2MSL 대기)
   CLOSED
```

1. **FIN**(클라이언트 → 서버): "보낼 데이터를 다 보냈어요." 클라이언트는 `FIN_WAIT_1`.
2. **ACK**(서버 → 클라이언트): "알겠어요." 서버는 `CLOSE_WAIT`, 클라이언트는 `FIN_WAIT_2`. 이때 서버는 아직 보낼 데이터가 남았다면 계속 보낼 수 있어요(한쪽만 닫힌 반 종료, Half-close).
3. **FIN**(서버 → 클라이언트): 서버도 다 보내면 FIN을 보내고 `LAST_ACK`.
4. **ACK**(클라이언트 → 서버): 서버는 이 ACK를 받으면 `CLOSED`. 클라이언트는 바로 닫지 않고 `TIME_WAIT`에서 잠시 기다려요.

### TIME_WAIT는 왜 필요할까

먼저 종료를 시작한 쪽은 마지막 ACK를 보낸 뒤 **2MSL** 동안 `TIME_WAIT` 상태로 머물러요. MSL(Maximum Segment Lifetime)은 세그먼트가 네트워크 안에 살아 있을 수 있는 최대 시간이에요.

- **마지막 ACK가 사라질 경우 대비**: ACK가 사라지면 서버가 FIN을 다시 보내요. 클라이언트가 아직 남아 있어야 ACK를 다시 보내 줄 수 있어요.
- **늦게 도착한 옛 세그먼트 정리**: 같은 IP·포트 조합으로 곧바로 새 연결을 맺었을 때, 이전 연결에서 길을 헤매던 세그먼트가 새 연결의 데이터로 잘못 섞이지 않도록 사라질 시간을 줘요.

> [!TIP]
> 상태 이름은 **누가 먼저 끊느냐**로 나눠 외워요. 먼저 끊는 쪽: `FIN_WAIT_1` → `FIN_WAIT_2` → `TIME_WAIT`. 나중에 끊는 쪽: `CLOSE_WAIT` → `LAST_ACK`. 서버에 `CLOSE_WAIT`가 계속 쌓인다면 상대는 끊었는데 서버 프로그램이 연결을 닫지 않고 있다는 신호예요.

FIN 대신 RST를 보내면 이런 절차 없이 연결이 즉시 끊겨요. 비정상 상황에서 쓰는 강제 종료예요.

## TCP 상태 한눈에 보기

| 상태 | 뜻 |
|---|---|
| `CLOSED` | 연결이 없음 |
| `LISTEN` | 서버가 연결 요청을 기다리는 중 |
| `SYN_SENT` | SYN을 보내고 SYN+ACK를 기다리는 중 |
| `SYN_RECEIVED` | SYN을 받고 SYN+ACK를 보낸 뒤 ACK를 기다리는 중 |
| `ESTABLISHED` | 연결 완료, 데이터를 주고받는 중 |
| `FIN_WAIT_1` | FIN을 보내고 ACK를 기다리는 중 |
| `FIN_WAIT_2` | 내 FIN의 ACK를 받고 상대의 FIN을 기다리는 중 |
| `CLOSE_WAIT` | 상대의 FIN을 받고 내 쪽이 닫기를 기다리는 중 |
| `LAST_ACK` | 내 FIN을 보내고 마지막 ACK를 기다리는 중 |
| `TIME_WAIT` | 마지막 ACK를 보낸 뒤 2MSL 동안 대기 |

양쪽이 동시에 FIN을 보내는 드문 경우에는 `CLOSING` 상태도 거쳐요. 실제 연결 상태는 다음 명령으로 볼 수 있어요. 표기는 도구마다 조금 달라서, 예를 들어 Windows는 `LISTENING`, 리눅스 `ss`는 `LISTEN`으로 보여 줘요.

```powershell
netstat -an     # Windows: 모든 연결과 상태를 숫자 주소로
netstat -ano    # 프로세스 ID(PID)까지 함께
```

```bash
ss -tan         # 리눅스: TCP 연결과 상태
```

## 흐름 제어 — 받는 쪽을 배려하기

보내는 쪽이 빠르고 받는 쪽이 느리면, 받는 쪽의 버퍼가 넘쳐 데이터가 버려져요. **흐름 제어**(Flow Control)는 받는 쪽이 "지금 이만큼까지만 보내세요"라고 알려 주는 방식으로 이 문제를 막아요.

받는 쪽은 TCP 헤더의 **윈도 크기** 필드에 남은 버퍼 공간(수신 윈도, rwnd)을 적어 보내요. 보내는 쪽은 아직 ACK를 받지 못한 데이터가 이 크기를 넘지 않도록 보내요. ACK가 도착할 때마다 보낼 수 있는 범위가 앞으로 밀려가므로 이를 **슬라이딩 윈도**(Sliding Window)라고 해요. 슬라이딩 윈도의 기본 개념은 [오류 제어와 흐름 제어](/textbook/net-error-flow-control)에서 배웠어요.

예를 들어 받는 쪽이 윈도 4,000을 알려 오면, 보내는 쪽은 MSS 1,000바이트짜리 세그먼트 4개를 ACK를 기다리지 않고 연달아 보낼 수 있어요. 받는 쪽 프로그램이 데이터를 늦게 가져가 버퍼가 꽉 차면 **윈도 0**(Zero Window)을 알려요. 그러면 보내는 쪽은 전송을 멈추고, 가끔 작은 확인용 세그먼트(윈도 탐색, Window Probe)를 보내 윈도가 다시 열렸는지 물어봐요.

## 혼잡 제어 — 네트워크를 배려하기

받는 쪽이 넉넉해도 중간 네트워크가 막혀 있으면 패킷이 사라져요. 모두가 계속 세게 보내면 재전송까지 겹쳐 네트워크가 더 막히죠. **혼잡 제어**(Congestion Control)는 보내는 쪽이 네트워크 상황을 짐작해 스스로 속도를 조절하는 방법이에요. 고속도로에 처음 들어설 때는 조심스럽게, 잘 뚫리면 점점 속도를 올리고, 정체가 보이면 확 줄이는 운전과 비슷해요.

보내는 쪽은 **혼잡 윈도**(cwnd, Congestion Window)라는 값을 스스로 관리해요. 실제로 한 번에 보낼 수 있는 양은 **수신 윈도(rwnd)와 혼잡 윈도(cwnd) 중 작은 값**이에요. 아래 설명은 이해하기 쉽게 cwnd를 MSS 개수로 셀게요.

| 단계 | 언제 | cwnd 변화 |
|---|---|---|
| 느린 시작(Slow Start) | 처음 시작할 때, 타임아웃 뒤 | 작은 값(교과서에서는 1 MSS)에서 시작해 ACK마다 1씩 늘어, **RTT마다 2배**가 돼요 |
| 혼잡 회피(Congestion Avoidance) | cwnd가 임계값(ssthresh)에 닿은 뒤 | **RTT마다 1 MSS씩** 천천히 늘려요 |
| 타임아웃 발생 | 심한 혼잡으로 판단 | ssthresh = 현재 cwnd의 절반, cwnd = 1로 줄이고 느린 시작부터 다시 |
| 중복 ACK 3번 | 가벼운 혼잡으로 판단 | 빠른 재전송 + 빠른 회복(아래 설명) |

"느린 시작"이라는 이름과 달리 증가 속도는 지수적으로 빨라요. 다만 **아주 작은 값에서 시작**하기 때문에 붙은 이름이에요. 이 증가를 언제 멈출지 정하는 기준이 **느린 시작 임계값**(ssthresh, Slow Start Threshold)이에요.

- **빠른 재전송(Fast Retransmit)**: 같은 ACK가 3번 더 오면(중복 ACK 3개), 재전송 타이머가 끝나기를 기다리지 않고 빠진 세그먼트를 바로 다시 보내요.
- **빠른 회복(Fast Recovery)**: 중복 ACK가 계속 온다는 것은 다른 세그먼트는 잘 도착하고 있다는 뜻이니 혼잡이 심하지 않다고 봐요. 그래서 cwnd를 1로 떨어뜨리지 않고 **절반으로만 줄인 뒤** 혼잡 회피를 이어 가요.

옛 방식인 TCP 타호(Tahoe)는 중복 ACK 3번에도 cwnd를 1로 줄였고, 이후의 TCP 리노(Reno)가 빠른 회복을 더했어요. 천천히 더하고(Additive Increase) 문제가 생기면 크게 나누는(Multiplicative Decrease) 이 방식을 **AIMD**라고 불러요.

### 단계별 예제

처음 cwnd = 1, ssthresh = 16이고, 9번째 RTT가 끝날 때 타임아웃이 일어났다고 해 봐요.

| RTT 차례 | cwnd | 단계 |
|---|---|---|
| 1 → 2 → 3 → 4 → 5 | 1 → 2 → 4 → 8 → 16 | 느린 시작(2배씩). 16에서 ssthresh에 닿음 |
| 6 → 7 → 8 → 9 | 17 → 18 → 19 → 20 | 혼잡 회피(1씩) |
| 타임아웃 | ssthresh = 20 ÷ 2 = 10, cwnd = 1 | 처음부터 다시 |
| 10 → 11 → 12 → 13 | 1 → 2 → 4 → 8 | 느린 시작 |
| 14 → 15 → 16 | 10 → 11 → 12 | ssthresh(10)를 넘지 않게 10에서 멈춘 뒤 혼잡 회피 |

만약 9번째 RTT에서 타임아웃이 아니라 **중복 ACK 3번**이 왔다면, 리노 방식에서는 ssthresh = 10, cwnd = 10으로 줄이고 바로 11, 12, … 처럼 혼잡 회피를 이어 가요.

> [!NOTE]
> 요즘 운영체제는 처음 cwnd를 더 크게 잡고 CUBIC, BBR 같은 발전된 알고리즘을 써요. 그래도 "작게 시작해 늘리고, 손실이 보이면 줄인다"는 뼈대는 같고, 시험은 위의 기본 원리를 기준으로 출제돼요.

> [!EXAM]
> - **흐름 제어**는 **받는 쪽**이 윈도 크기로 조절, **혼잡 제어**는 **보내는 쪽**이 네트워크 상황을 보고 cwnd로 조절해요. 둘을 맞바꾼 보기가 함정으로 잘 나와요.
> - 느린 시작은 지수 증가, 혼잡 회피는 선형 증가예요.
> - 중복 ACK 3번 → 빠른 재전송, 타임아웃 → cwnd를 1로 줄이고 느린 시작부터 다시

## 핵심 정리

- TCP는 연결 지향·신뢰성·순서 보장·전이중·바이트 스트림 프로토콜이며, 프로토콜 번호는 6, 데이터 단위는 세그먼트다.
- 헤더는 20–60바이트. 포트 각 16비트, 순서·확인 응답 번호 각 32비트, 윈도 16비트, 체크섬 16비트.
- 기본 플래그는 URG·ACK·PSH·RST·SYN·FIN, 혼잡 알림용으로 ECE·CWR이 추가되었다.
- 3-way 핸드셰이크: SYN → SYN+ACK → ACK. SYN과 FIN은 순서 번호를 1 차지한다.
- 확인 응답 번호 = 받은 순서 번호 + 데이터 길이(다음에 받을 바이트 번호).
- 4-way 종료: FIN → ACK → FIN → ACK. 먼저 끊은 쪽은 `TIME_WAIT`에서 2MSL 동안 기다린다.
- 흐름 제어는 수신 측 윈도 크기(rwnd), 혼잡 제어는 송신 측 혼잡 윈도(cwnd)로 한다. 실제 전송량은 둘 중 작은 값.
- 느린 시작(지수 증가) → ssthresh 도달 → 혼잡 회피(선형 증가). 중복 ACK 3번이면 빠른 재전송·빠른 회복.

## 스스로 확인하기

**1.** 3-way 핸드셰이크에서 서버가 클라이언트에게 보내는 두 번째 세그먼트에 켜지는 플래그는?
① SYN ② SYN, ACK ③ ACK ④ FIN, ACK

> [!ANSWER]
> 정답: ②
> 서버는 클라이언트의 SYN을 확인(ACK)하면서 동시에 자기 쪽 순서 번호도 알려야(SYN) 하므로 두 플래그를 함께 켜요.

**2.** 클라이언트가 순서 번호 2001로 700바이트 데이터를 담은 세그먼트를 보냈고, 서버가 오류 없이 받았어요. 서버가 돌려줄 확인 응답 번호는?
① 2001 ② 2700 ③ 2701 ④ 2702

> [!ANSWER]
> 정답: ③
> 2001번부터 700바이트면 2001–2700번 바이트예요. 다음에 받을 번호인 2001 + 700 = 2701을 확인 응답 번호로 보내요.

**3.** 연결 종료 과정에서 먼저 FIN을 보낸 쪽이 마지막 ACK를 보낸 뒤 일정 시간 머무르는 상태는?
① `CLOSE_WAIT` ② `LAST_ACK` ③ `TIME_WAIT` ④ `FIN_WAIT_2`

> [!ANSWER]
> 정답: ③
> 마지막 ACK가 사라졌을 때 다시 보내 주고, 늦게 도착한 옛 세그먼트가 사라지도록 2MSL 동안 `TIME_WAIT`에서 기다려요.

**4.** 받는 쪽이 TCP 헤더의 윈도 크기 필드로 자기 버퍼의 남은 공간을 알려, 보내는 쪽의 전송량을 조절하게 하는 기능은?
① 혼잡 제어 ② 흐름 제어 ③ 오류 제어 ④ 라우팅 제어

> [!ANSWER]
> 정답: ②
> 받는 쪽을 보호하는 것이 흐름 제어예요. 혼잡 제어는 보내는 쪽이 네트워크 상황을 보고 혼잡 윈도로 조절해요.

**5.** 처음 cwnd가 1 MSS, ssthresh가 8 MSS이고 손실이 전혀 없어요. 느린 시작은 RTT마다 2배, 혼잡 회피는 RTT마다 1 MSS씩 늘어난다고 할 때, RTT 5번이 지난 뒤 cwnd는?
① 9 MSS ② 10 MSS ③ 16 MSS ④ 32 MSS

> [!ANSWER]
> 정답: ②
> 1 → 2 → 4 → 8로 RTT 3번 만에 ssthresh에 닿고, 이후 혼잡 회피로 9 → 10이 되어 RTT 5번 뒤에는 10 MSS예요.
