전송 매체를 지나는 신호는 잡음과 감쇠 때문에 언제든 0이 1로, 1이 0으로 바뀔 수 있어요. 또 보내는 쪽이 너무 빠르면 받는 쪽이 미처 처리하지 못하고 데이터를 흘려 버리기도 해요. 이 단원에서는 오류를 찾아내고 고치는 방법(오류 제어)과 보내는 속도를 받는 쪽에 맞추는 방법(흐름 제어)을 배워요. CRC 계산, 해밍 코드의 패리티 비트 수, ARQ 방식 비교는 계산형·비교형 문제로 자주 나와요.

> [!GOAL]
> - 패리티·체크섬·CRC로 오류를 검출하는 원리를 설명하고, 간단한 CRC를 직접 계산할 수 있다.
> - 해밍 코드에 필요한 패리티 비트 수를 구하고, 1비트 오류의 위치를 찾을 수 있다.
> - FEC와 ARQ의 차이, 정지-대기·Go-Back-N·선택적 재전송 ARQ의 차이를 비교할 수 있다.
> - 슬라이딩 윈도우로 흐름 제어가 어떻게 이루어지는지 설명할 수 있다.

## 오류는 어떻게 생기고, 어떻게 다룰까

### 오류의 모양

- **단일 비트 오류(Single-bit Error)**: 데이터 중 한 비트만 바뀐 경우예요.
- **버스트 오류(Burst Error)**: 연속된 여러 비트가 한꺼번에 망가진 경우예요. 번개나 순간적인 전기 잡음은 짧은 순간에 여러 비트를 덮치기 때문에, 실제 통신에서는 버스트 오류가 흔해요.

오류를 다루려면 원래 데이터 말고 **검사용 비트**(잉여 비트, Redundant Bit)를 조금 더 붙여 보내야 해요. 받는 쪽은 이 잉여 비트를 보고 "뭔가 바뀌었다"를 알아채거나, 더 나아가 "몇 번째 비트가 바뀌었다"까지 알아내요.

### 검출 후 재전송이냐, 받는 쪽에서 직접 고치느냐

| 구분 | 전진 오류 수정 FEC | 후진 오류 수정 BEC(ARQ) |
|---|---|---|
| 원어 | Forward Error Correction | Backward Error Correction |
| 방법 | 잉여 비트를 넉넉히 붙여 수신 측이 스스로 오류를 찾아 고침 | 수신 측은 오류 검출만 하고, 송신 측에 재전송을 요청 |
| 역채널(되돌려 보내는 길) | 필요 없음 | 필요함(ACK·NAK를 보내야 하므로) |
| 잉여 비트 | 많음 | 적음 |
| 대표 기법 | 해밍 코드, 컨볼루션 코드, 리드-솔로몬 코드 | 패리티·체크섬·CRC로 검출 + ARQ로 재전송 |
| 어울리는 곳 | 재전송이 어렵거나 늦는 곳(위성, 방송, 실시간 영상) | 일반적인 데이터 통신 |

> [!TIP]
> 시험지를 친구에게 보낸다고 해 보세요. FEC는 답안지에 풀이 과정을 꼼꼼히 적어 보내서 받는 사람이 틀린 글자를 스스로 고칠 수 있게 하는 방식이고, ARQ는 "글자가 번졌으니 다시 보내 줘"라고 전화로 부탁하는 방식이에요.

## 패리티 검사

### 짝수 패리티와 홀수 패리티

패리티 검사(Parity Check)는 데이터 뒤에 비트 하나를 덧붙여 **1의 개수**를 맞추는 가장 단순한 방법이에요.

- **짝수 패리티(Even Parity)**: 패리티 비트까지 포함한 1의 개수가 짝수가 되도록 해요.
- **홀수 패리티(Odd Parity)**: 패리티 비트까지 포함한 1의 개수가 홀수가 되도록 해요.

예를 들어 7비트 데이터 `1011001`에는 1이 4개 있어요.

| 방식 | 패리티 비트 | 전송 비트열 | 전체 1의 개수 |
|---|---|---|---|
| 짝수 패리티 | 0 | `10110010` | 4개(짝수) |
| 홀수 패리티 | 1 | `10110011` | 5개(홀수) |

받는 쪽은 1의 개수를 세어 약속과 다르면 오류로 판단해요.

> [!WARNING]
> 패리티는 **홀수 개의 비트**가 바뀐 경우만 찾아요. 두 비트가 동시에 바뀌면 1의 개수의 짝·홀이 그대로라서 오류를 놓쳐요. 또 어느 비트가 틀렸는지 모르므로 오류를 **고치지는 못해요**.

### 2차원 패리티

문자 하나하나마다 패리티 비트를 붙이는 것을 **VRC(Vertical Redundancy Check, 수직 중복 검사)**, 여러 문자를 한 블록으로 묶어 같은 자리 비트끼리 패리티를 계산한 뒤 블록 끝에 한 문자로 붙이는 것을 **LRC**(Longitudinal Redundancy Check, 흔히 수평 중복 검사)라고 해요. 표의 행과 열에 각각 패리티를 단 것과 같아서, 둘을 함께 쓰면 행 패리티와 열 패리티가 동시에 어긋나는 교차점에서 1비트 오류의 위치까지 찾을 수 있어요.

## 체크섬

체크섬(Checksum)은 데이터를 일정한 길이의 덩어리로 나눠 모두 더한 값을 함께 보내는 방법이에요. 인터넷에서는 16비트 단위로 **1의 보수 덧셈**을 하고, 결과를 다시 뒤집은(1의 보수) 값을 체크섬으로 써요. IP·TCP·UDP 헤더가 이 방식을 사용해요.

원리만 4비트로 줄여서 보면 이래요. 데이터가 `0111`, `1010` 두 덩어리라고 해요.

```text
송신 측
  0111 + 1010 = 1 0001   (자리올림 1 발생)
  넘친 1을 맨 뒤에 다시 더함: 0001 + 1 = 0010
  뒤집기(1의 보수): 0010 -> 1101   ← 체크섬

수신 측
  0111 + 1010 + 1101 = 1 1110
  넘친 1을 다시 더함: 1110 + 1 = 1111
  뒤집기: 1111 -> 0000   ← 0이면 오류 없음
```

체크섬은 계산이 간단하지만 CRC보다 검출 능력이 약해요. 자세한 헤더 구조는 [IP 패킷의 구조와 단편화](/textbook/tcpip-ip-header)에서 다시 봐요.

## CRC 순환 중복 검사

### 원리

CRC(Cyclic Redundancy Check, 순환 중복 검사)는 데이터를 하나의 긴 2진수로 보고, 송수신 측이 미리 약속한 **생성 다항식**(Generator Polynomial)으로 나눈 **나머지**를 검사 비트로 붙이는 방법이에요. 이 나머지를 FCS(Frame Check Sequence)라고도 불러요. 이더넷 프레임 끝의 FCS가 바로 CRC-32 값이에요.

여기서 나눗셈은 일반 나눗셈이 아니라 **모듈로-2 연산**으로 해요. 자리올림과 자리내림이 없고, 빼기 대신 **XOR**를 해요. XOR는 두 비트가 같으면 0, 다르면 1이에요.

계산 순서는 다음과 같아요.

1. 생성 다항식을 비트열로 바꿔요. 최고 차수가 r이면 비트열은 r+1자리예요.
2. 데이터 뒤에 0을 **r개** 붙여요.
3. 그 비트열을 생성 비트열로 모듈로-2 나눗셈해요. 맨 앞자리가 1이면 생성 비트열과 XOR, 0이면 0000…과 XOR(사실상 그대로) 해요.
4. 남은 r비트 나머지가 CRC예요. 원래 데이터 뒤에 이 나머지를 붙여 보내요.
5. 수신 측은 받은 비트열 전체를 같은 생성 비트열로 나눠서, **나머지가 0이면 오류 없음**, 0이 아니면 오류로 판단해요.

### 단계별 예제

데이터 `110101`을 생성 다항식 `x³ + x + 1`로 보호해 볼게요.

**1단계 — 생성 다항식을 비트열로.** 각 차수의 계수를 높은 차수부터 적어요.

```text
x³   x²   x¹   x⁰
 1    0    1    1    → 생성 비트열 1011 (최고 차수 r = 3)
```

**2단계 — 데이터 뒤에 0을 3개.** `110101` → `110101000`

**3단계 — 모듈로-2 나눗셈.** 앞에서부터 4비트씩 잘라 XOR하고, 결과의 맨 앞 0을 버린 뒤 다음 비트를 하나 내려요.

```text
  110101000
  1011
  ----
   1100
   1011
   ----
    1111
    1011
    ----
     1000
     1011
     ----
      0110
      0000
      ----
       1100
       1011
       ----
        111
```

같은 과정을 말로 풀면 이래요.

| 단계 | 현재 4비트 | XOR 값 | 결과 | 다음에 내릴 비트 |
|---|---|---|---|---|
| 1 | 1101 | 1011 | 0110 | 0 → 1100 |
| 2 | 1100 | 1011 | 0111 | 1 → 1111 |
| 3 | 1111 | 1011 | 0100 | 0 → 1000 |
| 4 | 1000 | 1011 | 0011 | 0 → 0110 |
| 5 | 0110 | 0000(맨 앞이 0) | 0110 | 0 → 1100 |
| 6 | 1100 | 1011 | 0111 | 없음 → 나머지 111 |

**4단계 — 나머지 붙이기.** 나머지는 `111`이에요. 보내는 비트열은 데이터 + CRC = `110101` + `111` = `110101111`이에요.

**5단계 — 수신 측 확인.** 수신 측이 `110101111`을 `1011`로 모듈로-2 나눗셈하면 나머지가 `000`이 나와요. 전송 중 어느 비트가 바뀌었다면 대부분 나머지가 0이 아니게 되어 오류를 알아채요.

> [!TIP]
> 헷갈릴 때는 두 가지만 기억하세요. "**붙이는 0의 개수 = 생성 다항식의 최고 차수 = CRC 비트 수**", 그리고 "**빼기 대신 XOR**". 생성 비트열의 길이는 차수보다 한 자리 길어요.

### CRC의 특징

- 하드웨어(시프트 레지스터와 XOR 회로)로 아주 빠르게 계산할 수 있어요.
- 생성 다항식을 잘 고르면 최고 차수 이하 길이의 **버스트 오류를 모두 검출**할 수 있어서 패리티나 체크섬보다 훨씬 강력해요.
- 대표 규격으로 CRC-16, CRC-CCITT, CRC-32가 있고, 이더넷과 HDLC 등 데이터 링크 계층에서 널리 써요.
- 오류를 **검출**하는 기법이라 고치는 것은 재전송(ARQ)에 맡겨요.

> [!EXAM]
> "생성 다항식이 x⁵ + x² + 1일 때 CRC는 몇 비트인가?"처럼 최고 차수만 보면 바로 풀리는 문제가 나와요. 답은 5비트예요. 직접 나눗셈을 시키는 문제도 나오니 위 예제를 손으로 한 번 따라 해 보세요.

## 해밍 코드

### 개념

해밍 코드(Hamming Code)는 여러 개의 패리티 비트를 정해진 자리에 끼워 넣어서, **1비트 오류가 어디서 났는지 위치까지 찾아 고칠 수 있는** 대표적인 FEC 기법이에요. 패리티 비트를 하나 더 붙인 확장 해밍 코드는 1비트 오류 정정에 더해 2비트 오류 검출까지 할 수 있어요.

### 패리티 비트 수 구하기

데이터 비트가 d개일 때 필요한 패리티 비트 수 p는 다음 식을 만족하는 **가장 작은 p**예요.

```text
2^p ≥ d + p + 1
```

p개의 패리티 비트로 만들 수 있는 경우의 수는 `2^p`가지예요. 이것으로 "오류 없음" 1가지와 "전체 d + p개 비트 중 몇 번째가 틀렸는지"를 모두 구분해야 하므로 위 식이 나와요.

| 데이터 비트 d | p를 하나씩 넣어 보기 | 패리티 비트 p | 전체 비트 |
|---|---|---|---|
| 4 | p=2: 4 ≥ 7 실패 / p=3: 8 ≥ 8 성공 | 3 | 7 |
| 7 | p=3: 8 ≥ 11 실패 / p=4: 16 ≥ 12 성공 | 4 | 11 |
| 8 | p=3: 8 ≥ 12 실패 / p=4: 16 ≥ 13 성공 | 4 | 12 |
| 16 | p=4: 16 ≥ 21 실패 / p=5: 32 ≥ 22 성공 | 5 | 21 |
| 32 | p=5: 32 ≥ 38 실패 / p=6: 64 ≥ 39 성공 | 6 | 38 |

### 패리티 비트의 자리와 검사 범위

패리티 비트는 **2의 거듭제곱 자리**(1, 2, 4, 8, …)에 놓고, 나머지 자리에 데이터를 차례로 넣어요. 데이터가 4비트이면 이렇게 돼요.

```text
위치  1   2   3   4   5   6   7
역할  P1  P2  D1  P4  D2  D3  D4
```

각 패리티 비트는 위치 번호를 2진수로 썼을 때 자기 자리 비트가 1인 위치들을 맡아요.

| 패리티 | 맡는 위치 | 이유 |
|---|---|---|
| P1 | 1, 3, 5, 7 | 2진수 맨 끝(1의 자리)이 1인 위치 |
| P2 | 2, 3, 6, 7 | 2의 자리가 1인 위치 |
| P4 | 4, 5, 6, 7 | 4의 자리가 1인 위치 |

### 단계별 예제 — 만들기와 고치기

데이터 `1011`을 짝수 패리티 해밍 코드로 만들어 볼게요. D1=1, D2=0, D3=1, D4=1이므로 위치 3=1, 5=0, 6=1, 7=1이에요.

```text
P1 = 위치3 ⊕ 위치5 ⊕ 위치7 = 1 ⊕ 0 ⊕ 1 = 0
P2 = 위치3 ⊕ 위치6 ⊕ 위치7 = 1 ⊕ 1 ⊕ 1 = 1
P4 = 위치5 ⊕ 위치6 ⊕ 위치7 = 0 ⊕ 1 ⊕ 1 = 0

위치  1 2 3 4 5 6 7
비트  0 1 1 0 0 1 1   → 보내는 부호: 0110011
```

전송 중 6번 위치가 바뀌어 `0110001`이 도착했다고 해 봐요. 수신 측은 각 검사 범위의 XOR를 다시 계산해요.

```text
C1 = 위치1 ⊕ 3 ⊕ 5 ⊕ 7 = 0 ⊕ 1 ⊕ 0 ⊕ 1 = 0
C2 = 위치2 ⊕ 3 ⊕ 6 ⊕ 7 = 1 ⊕ 1 ⊕ 0 ⊕ 1 = 1
C4 = 위치4 ⊕ 5 ⊕ 6 ⊕ 7 = 0 ⊕ 0 ⊕ 0 ⊕ 1 = 1

C4 C2 C1 = 1 1 0 (2진수) = 6  → 6번 비트를 뒤집으면 원래 0110011
```

검사 결과가 모두 0이면 오류가 없는 것이고, 0이 아니면 그 2진수 값이 바로 **틀린 비트의 위치**예요.

> [!EXAM]
> "수신 측에서 스스로 오류를 정정할 수 있는 코드"를 고르라면 해밍 코드예요. 패리티·체크섬·CRC는 **검출만** 하고, 해밍 코드는 **1비트 오류 정정**까지 해요. 데이터 비트 수를 주고 패리티 비트 수를 묻는 계산 문제도 위 식으로 p를 하나씩 넣어 보면 바로 풀려요.

### 해밍 거리

두 비트열에서 **서로 다른 자리의 개수**를 해밍 거리(Hamming Distance)라고 해요. `1011001`과 `1001101`은 3번째와 5번째 자리가 달라서 해밍 거리가 2예요. 부호들 사이의 최소 해밍 거리가 클수록 오류에 강해요. 일반적으로 s개 오류를 검출하려면 최소 거리가 s+1 이상, t개 오류를 정정하려면 2t+1 이상이어야 해요.

## ARQ 자동 반복 요청

ARQ(Automatic Repeat reQuest)는 오류를 검출하면 재전송을 요청해 고치는 방식이에요. 다음 도구를 함께 써요.

- **ACK(긍정 응답)**: 잘 받았다는 신호
- **NAK(부정 응답)**: 오류가 있으니 다시 보내 달라는 신호
- **타이머**: 일정 시간 안에 응답이 없으면(프레임이나 ACK가 사라졌으면) 다시 보냄
- **순서 번호**: 프레임과 응답이 어느 것인지 구별하고, 중복 수신을 걸러 냄

### 정지-대기 ARQ

정지-대기 ARQ(Stop-and-Wait ARQ)는 프레임을 **하나 보내고 ACK가 올 때까지 기다리는** 방식이에요. 구현이 가장 쉽고 버퍼도 한 프레임이면 되지만, 기다리는 시간 동안 회선이 놀아요. 특히 위성처럼 왕복 시간이 긴 회선에서는 효율이 크게 떨어져요. 순서 번호는 0과 1 두 가지만 번갈아 써도 충분해요.

### 연속적 ARQ — Go-Back-N과 선택적 재전송

ACK를 기다리지 않고 여러 프레임을 연달아 보내는 방식을 연속적 ARQ(Continuous ARQ)라고 하고, 오류가 났을 때 무엇을 다시 보내느냐에 따라 둘로 나뉘어요.

- **Go-Back-N ARQ**: 오류가 난 프레임부터 **그 뒤에 보낸 프레임까지 전부** 다시 보내요. 수신 측은 순서가 어긋난 프레임을 저장하지 않고 버리므로 구조가 단순해요.
- **선택적 재전송 ARQ(Selective Repeat ARQ)**: **오류가 난 프레임만** 다시 보내요. 수신 측은 뒤에 먼저 도착한 프레임을 버퍼에 보관했다가 빠진 프레임이 오면 순서대로 다시 맞춰야 해서 버퍼와 처리 로직이 더 필요해요.

0번부터 6번까지 연달아 보냈는데 2번만 손상되었다면 이렇게 달라요.

| 프레임 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| 수신 결과 | 정상 | 정상 | 손상 | 정상 | 정상 | 정상 | 정상 |
| Go-Back-N 재전송 | | | 다시 | 다시 | 다시 | 다시 | 다시 |
| 선택적 재전송 | | | 다시 | | | | |

### 적응적 ARQ

적응적 ARQ(Adaptive ARQ)는 회선 상태에 따라 **프레임 길이를 바꿔 가며** 보내는 방식이에요. 오류가 적을 때는 프레임을 길게 해서 효율을 높이고, 오류가 많을 때는 짧게 해서 재전송 부담을 줄여요. 효율은 좋지만 제어가 복잡해요.

### ARQ 방식 비교

| 항목 | 정지-대기 | Go-Back-N | 선택적 재전송 |
|---|---|---|---|
| 한 번에 보내는 프레임 | 1개 | 윈도우 크기만큼 연속 | 윈도우 크기만큼 연속 |
| 오류 시 재전송 범위 | 그 프레임 | 오류 프레임부터 이후 전부 | 오류 프레임만 |
| 수신 측 버퍼 | 1프레임 | 1프레임(순서 어긋나면 버림) | 여러 프레임(재정렬 필요) |
| 구현 복잡도 | 가장 단순 | 중간 | 가장 복잡 |
| 회선 효율 | 낮음 | 높음(불필요한 재전송 있음) | 가장 높음 |
| 최대 송신 윈도우(순서 번호 m비트) | 1 | 2^m − 1 | 2^(m−1) |

> [!EXAM]
> "오류 프레임 이후 모든 프레임을 재전송" → Go-Back-N, "오류 프레임만 재전송, 수신 측 재정렬 필요" → 선택적 재전송, "프레임 길이를 동적으로 변경" → 적응적 ARQ, "한 프레임 보내고 응답 대기" → 정지-대기. 설명을 보고 이름을 고르는 형태로 자주 나와요.

## 흐름 제어와 슬라이딩 윈도우

### 흐름 제어가 왜 필요할까

흐름 제어(Flow Control)는 **받는 쪽이 감당할 수 있는 만큼만 보내도록** 송신 속도를 조절하는 일이에요. 빠른 서버가 느린 기기에 쉬지 않고 데이터를 쏟아부으면 수신 버퍼가 넘쳐 데이터가 버려지고, 결국 재전송이 늘어나 오히려 느려져요. 가장 단순한 흐름 제어가 앞에서 본 정지-대기 방식이고, 더 효율적인 방법이 슬라이딩 윈도우예요.

### 슬라이딩 윈도우

슬라이딩 윈도우(Sliding Window)는 **ACK 없이 연달아 보낼 수 있는 프레임 수**(윈도우 크기)를 정해 두고, ACK가 도착할 때마다 그 창을 앞으로 미는 방식이에요.

순서 번호가 3비트(0~7을 돌려 씀)이고 송신 윈도우 크기가 4라고 해 봐요.

```text
(1) 처음: 0~3번까지 ACK 없이 보낼 수 있다
[0 1 2 3] 4 5 6 7 0 1 2 ...

(2) 0번과 1번이 잘 도착했다는 ACK를 받으면 창이 두 칸 이동
 0 1 [2 3 4 5] 6 7 0 1 2 ...

(3) 이제 4번과 5번을 새로 보낼 수 있다
```

- 윈도우 안의 프레임은 "보냈지만 아직 ACK를 못 받은 것"과 "지금 보내도 되는 것"이에요.
- 수신 측이 바쁘면 윈도우 크기를 줄이라고 알려서 송신 속도를 늦출 수 있어요. 윈도우 크기가 1이면 정지-대기와 같아져요.
- 윈도우 덕분에 회선을 쉬지 않고 쓰면서도 수신 측이 넘치지 않게 할 수 있어요.

> [!NOTE]
> 양쪽이 서로 데이터를 주고받을 때, 따로 ACK 프레임을 만들지 않고 **반대 방향으로 가는 데이터 프레임에 ACK를 얹어 보내는** 기법을 피기배킹(Piggybacking)이라고 해요. 회선 낭비를 줄여 줘요.

> [!WARNING]
> 흐름 제어는 **송신자와 수신자 둘 사이**의 문제(받는 쪽 처리 능력)이고, 혼잡 제어(Congestion Control)는 **네트워크 전체**가 붐비는 문제예요. 이름이 비슷해 보기에서 섞어 내니 구분해 두세요. TCP의 흐름·혼잡 제어는 [TCP](/textbook/tcpip-tcp)에서 자세히 배워요.

## 핵심 정리

- FEC는 수신 측이 스스로 고침(역채널 불필요, 해밍 코드 등), BEC는 검출 후 재전송 요청(ARQ, 역채널 필요).
- 패리티는 홀수 개 비트 오류만 검출하고 정정은 못 한다. 짝수 패리티는 1의 개수를 짝수로, 홀수 패리티는 홀수로 맞춘다.
- 체크섬은 덩어리를 1의 보수로 더한 뒤 뒤집은 값으로, IP·TCP·UDP 헤더에서 쓴다.
- CRC는 데이터 뒤에 0을 r개(생성 다항식 최고 차수) 붙여 모듈로-2(XOR) 나눗셈한 나머지를 붙인다. 수신 측 나머지가 0이면 정상. 버스트 오류에 강하다.
- 해밍 코드 패리티 비트 수는 `2^p ≥ d + p + 1`을 만족하는 최소 p. 패리티는 1·2·4·8… 자리에 둔다. 1비트 오류 정정 가능.
- 정지-대기는 하나 보내고 대기, Go-Back-N은 오류 프레임부터 전부 재전송, 선택적 재전송은 오류 프레임만, 적응적 ARQ는 프레임 길이를 바꾼다.
- 슬라이딩 윈도우는 ACK 없이 보낼 수 있는 프레임 수를 정하고 ACK가 오면 창을 밀어 흐름을 제어한다.

## 스스로 확인하기

**1.** 데이터 비트가 11비트일 때 해밍 코드로 1비트 오류를 정정하려면 최소 몇 개의 패리티 비트가 필요할까요?
① 3개 ② 4개 ③ 5개 ④ 6개

> [!ANSWER]
> 정답: ②
> p=3이면 2³=8 ≥ 11+3+1=15를 만족하지 못해요. p=4이면 2⁴=16 ≥ 11+4+1=16을 만족하므로 최소 4개예요.

**2.** 데이터 `1101`을 생성 다항식 `x² + 1`(비트열 `101`)로 CRC 처리할 때 붙는 나머지는?
① 00 ② 01 ③ 10 ④ 11

> [!ANSWER]
> 정답: ③
> 최고 차수가 2이므로 0을 두 개 붙인 `110100`을 `101`로 나눠요. 110⊕101=011 → 1을 내려 111 → 111⊕101=010 → 0을 내려 100 → 100⊕101=001 → 0을 내려 010 → 맨 앞이 0이라 그대로 두면 나머지는 `10`이에요.

**3.** 민수가 7개의 프레임(0~6번)을 연달아 보냈는데 4번 프레임만 손상되었어요. Go-Back-N ARQ를 쓸 때 다시 보내야 하는 프레임의 개수는?
① 1개 ② 2개 ③ 3개 ④ 5개

> [!ANSWER]
> 정답: ③
> Go-Back-N은 오류가 난 4번부터 그 뒤의 5번, 6번까지 모두 다시 보내므로 3개예요. 선택적 재전송이라면 4번 1개만 다시 보내요.

**4.** 짝수 패리티를 쓰는 통신에서 수신 측이 `11010110`을 받았어요(마지막 비트가 패리티). 이 결과에 대한 설명으로 옳은 것은?
① 1의 개수가 홀수이므로 오류로 판단한다. ② 1의 개수가 짝수이므로 오류가 없다고 판단한다. ③ 몇 번째 비트가 틀렸는지 찾아 고친다. ④ 2비트 오류임을 정확히 알아낸다.

> [!ANSWER]
> 정답: ①
> 1이 5개(홀수)라서 짝수 패리티 약속과 맞지 않으므로 오류로 판단해요. 패리티 비트 하나로는 어느 비트가 틀렸는지 알 수 없어서 고치지는 못해요.
